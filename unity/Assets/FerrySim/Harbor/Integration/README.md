# Harbor integration

`FerrySim.Harbor.Integration` is the harbor scene's composition root: `HarborIntegrationFactory`, the `HarborSceneServiceFactory` that `HarborSceneBuilder` puts on the "Harbor composition" object beside `HarborBootstrap`. `Create(context)` verifies the runtime pack and prepares the resident services; the bootstrap connects them (`Harbor/README.md`, Integration). Nothing here loads, samples, replays or simulates on its own.

| Service | Real implementation |
|---|---|
| Water | `HarborWaterForwarder`, one stable `IWaterSurface` over the runtime pack's canonical datum. Each environment-backed harbor start or replay binds that run's `HarborWaterService` (datum plus `RunEnvironment.WaterLevel`), subscribed before the navigation and traffic builders so it is bound before they react and before the vessel is first placed. Before the first run it is the datum alone, NAVD88 zero with no tide, so the navigation geometry can be anchored; it never extrapolates. |
| Visual water | One `HarborWaterPatch` per depth grid (40 × 40 cells of 100 m) under the water root, with the shared `World/Materials/Water.mat`, driven by the runner's `RenderTime`. Matching patch coordinates/shape, datum nodes/mask and ordered gauge locations reuse the baked mesh; changed layouts rebuild. Each start binds the new run's tide observer. |
| Runtime pack | `HarborRuntimePackJson.Load` of `runtimePackFolder`; the scene binds this verified snapshot into the runner's `EnvironmentPacks`, so starts share the same instance and digest without another load or query index. |
| Landings | The verified runtime pack's contacts text, checked against `contactsFile` at composition and parsed once with `Data/landing-contact-surfaces.json`; starts share its geometry instance. |
| Catalog | `HarborScenarioCatalog` over the landings, both vessel files, the runner's `EnvironmentPacks` and `TrafficPacks`, the landing audit's marks and `SharedDepthEnvironments`, which previews depth through `EnvironmentPacks.LoadHarborDay` so the verified depth set and selected immutable day are shared by preview and atomic start. |
| Launcher | `HarborLauncher`: `VesselSimulationRunner.InitializeHarbor` with the slice contact parser and `FaceClearance` as the start gate, so a refused candidate leaves the current run going. |
| Navigation | `HarborNavigationWorld.Build` with the pack, the georeference, the forwarding water and the sun's `Atmosphere`, then `Follow(runner, camera)`. The picker's landing selection sets `SelectedStopId`. |
| Traffic | `TrafficView.ConnectHarbor` with the forwarding water and `HarborTrafficCoverage`, the active tiles of `data/processed/harbor/index.json`. |
| Holds | `HarborBootstrap` shows the runner's `IRunHoldSource` hold in its status line; a new start resumes. |
| Chart | `HarborChartLoad.Start` of the `chart` folder beside the runtime pack, once per process on a thread-pool thread, started when the scene composes so no start waits on the seconds the verified load takes (about 8 s in the editor). The same folder and runtime digest share one load, so a reloaded scene keeps the one copy. The worker also builds the radar's semantic index and the chartplotter's tessellation; only immutable data crosses the thread. |
| Displays | `HarborDisplays` composes the own interior’s console screens and shared HUD pictures against the ready chart load. Flat chartplotter and compact radar overlays connect lazily when console screens are off or an interior is unavailable. A shown fallback announces CHART LOADING or CHART ERROR until the shared data is ready. |

## v0.5 presentation composition

`HarborDisplays` creates one `ConsoleScreens` host beside the overlay document when the running own vessel has an active interior. The four authored surface mounts use the console targets; `WheelhouseView.ScreenSource` gives HUD pop-outs the exact same texture objects. Console screens are enabled by default. The first-launch HUD stays `classic`; readable lean-in poses come from the prefab's focus mounts.

The composition sends wheelhouse visibility, effective HUD pop-out visibility and the camera's focused mount to the console scheduler. Picker, options and debrief hide viewer demand. Chase/free-fly stop the wheelhouse demand while independently visible pop-outs can still demand their pictures. Demanded panels remain live between data refreshes. Flat radar and chartplotter components are connected lazily when console screens are disabled or an interior is unavailable, and hidden flat displays do not refresh alongside console views. A run/class change releases the previous native targets before creating the replacement interior's screens.

`1` and `2` use the registered Displays action map. With console screens active they toggle transient plotter/radar HUD pop-outs through `HudController.ToggleSessionShown`; this does not mark the saved layout modified or write preferences. Choosing a layout resets those session choices. Programmatic `RadarShown`, `ChartplotterShown` and `ToggleRadar`/`ToggleChartplotter` continue to request the legacy flat overlays, including benchmark callers. Without console screens the keys toggle those overlays. Other display controls act on the active console instrument or visible flat fallback. Per-instrument palette-key choices survive refresh, day/night and run changes; explicitly changing the global palette setting replaces those choices.

`HarborPresentation` connects saved display/plotter settings, look sensitivity, master/mute/alarm audio gains and key-hint mode at creation and on settings changes. The audio rig's mute-key event writes back only mute. Explicit command-line audio volume and silent tests/smoke defaults take precedence over saved master volume without changing the file. `HarborLaunchPreferences` prepares temporary stores before UI enable for route/smoke and explicit presentation overrides; normal interactive launches retain the player's settings. Existing route/smoke presentation defaults remain flat screens with the classic preset. Benchmark switches are `-ferrysim-console-screens 0|1` and `-ferrysim-hud-preset classic|console|minimal|everything`.

`HarborBootstrap` aggregates picker and options visibility into one pause owner. The last dialog close resumes only a run those dialogs paused. Either dialog, or HUD-layout text focus, holds helm input. `HarborPresentation` creates the interior key-hint layer, binds its control map, camera and binding service, and reattaches it above the rebuilt HUD document. Menus suppress hints. Run/class changes replace its interior binding.

A registered Alarms map forwards acknowledge, silence and held lamp test to the running runner's `IInstrumentSource`. A new run releases lamp test. `HarborHudDisplayInput` maps the shared alarm and both engine images' letterboxed pointer coordinates to existing skin softkeys and preserves pointer capture for held keys; it cancels on hiding or replacing the source. There is no second alarm view or render. Missing instrument data is harmless.

Every harbor consumer owns and unregisters its action asset: helm, the camera readers, interface menu reader, audio rig, display mapper, presentation alarm map and hint reader. Display assets copied from the helm are explicitly registered as well. Lifecycle tests cover a second composition releasing the runtime pack, console targets and old hint layer.

## Landing audit

`Data/landing-audit.json` is written from `python -m ferrydata.harbor_landings matrix` on the adopted harbor packs (`data-pipeline/ferrydata/harbor_landings/README.md`): per berth, whether it has a start pose and, per hull, how many of the 700 sampled starts (28 days × 25 samples) were afloat. `HarborLandingAudit` turns each berth with a start pose into a `HarborBerthMark` whose note the picker shows beside the berth ("Landing audit: afloat at every sampled tide", or "Landing audit: afloat T 467/700 · K 598/700"); the three faces without a start pose keep the catalog's crew-answer note. The audit refuses nothing: an aground start is still refused per tide by the catalog. The factory refuses an audit assessed on another depth set than the runtime pack links. `matrix_provenance` retains the assessed depth digest, contacts hash, vessel-file hashes, day digests and the `berths.json` hash. The writer requires that provenance beside `berths.json`, refuses a different adopted depth, changed output or changed vessel file, and the runtime parser rechecks both shipped vessel hashes before publishing any marks.

Regenerate it after a depth or matrix change, from the repository root, with the matrix's `berths.json`:

```sh
PYTHONPATH=data-pipeline uv run --project data-pipeline python -m ferrydata.harbor_landings matrix \
  --contacts data/processed/harbor/unity/contacts.json --env data/processed/harbor/env --out artifacts/harbor-integration/matrix-after
PYTHONPATH=data-pipeline uv run --project data-pipeline python unity/Assets/FerrySim/Harbor/Data/write_landing_audit.py \
  artifacts/harbor-integration/matrix-after/berths.json data/processed/harbor/env/depth/DIGEST unity/Assets/FerrySim/Harbor/Data/landing-audit.json
```

## Verification

`Harbor/Tests/Integration/EditMode` covers the forwarder (datum only before a run, the run's service after, refusal outside the lattice), the audit's marks and refusals, the traffic coverage, the hold text and the chart load (a start that never waits, one load per key and no second copy, a failure reported with its file). `HarborDisplaysPlayTests` runs the real scene: a Pier 11 start before the chart is ready, both displays toggled on and connected when it is, 30 s under way, own ship and the targets on the plotter against the runner's state, the radar's heading line and the echoes of Pier 11's shore and a Brooklyn Bridge span on their bearings, the calibrated `GC.Alloc` guard with both on, hiding in the chase view and under the picker, reconnection on a new run and a replay, and the recording digest with and without the displays. `HarborDisplaysCaptureTests` is explicit: Pier 11 by day and night and the Upper Bay with traffic, the wheelhouse with both displays, under `artifacts/integration-fixes/captures`. `Harbor/Tests/Integration/PlayMode` loads `Harbor.unity` with the real services and data (ignored, naming the folder, when `data/processed/harbor` is not copied): a start at Pier 11 on a traffic day, St. George refused through the picker with its reason shown, the run stepping on the run's water with the visual patches under the hull, 28 barges and 285 drawn aids, traffic present, and a hold with its explanation when a fixture start leaves covered water. `HarborIntegrationCaptureTests` is explicit: Pier 11 by day and night, the Brooklyn Bridge and St. George from the wheelhouse and the chase view, under `artifacts/harbor-integration/captures`.

The factory assigns its captured default `EnvironmentPacks` back to the runner before constructing the catalog, so preview and active runs share the same verified depth object across days. The general harbor load path used by replay reuses that verified set too; the slice loader is unchanged. Replay binds against its recorded `RunEnvironment`, using the scene's verified runtime datum when the replay has no runtime pack; water and patches bind before navigation, traffic and first placement. `HarborReplayTests` exercises the actual default scene, including replay before any ordinary run.

## Start transitions and picker selection

`EnvironmentPacks` retains one verified depth set, one selected day keyed by its exact folder and digest, and the scene's runtime/contact snapshot. A different day replaces the selected cache; a successful commit releases the catalog's preview observer. The active run remains intact until every candidate, vessel, start gate and core check succeeds. Only immutable pack data is shared; observers, physics environments and traffic monitors remain per run. No traffic-day cache or background decoder is added.

Before preparing a switch candidate, the runner collects retired runs and decoding temporaries synchronously, while still in the start transition. A fresh runner has no retired run and skips that collection. `HarborLoadTimings` reports collection time and managed bytes reclaimed, vessel/start-gate work, core creation, binding time and the full synchronous transition, in addition to the existing depth/day/runtime/contact/traffic phases. Collection cannot run after that start's first full view. Its byte counter is managed used memory, not the installed player's System Used Memory budget.

The navigation label follows the picker highlight while the picker is visible. An accepted start remembers its exact catalog stop independently of later highlights; closing a refused or dismissed choice restores that active stop, or clears the label when no run is active. Replacing the wheelhouse view detaches the old selection, start and visibility handlers before binding the new picker. Catalog-created settings carry a weak association with their stop, so programmatic starts have the same identity without retaining old settings or inferring a stop from a formatted name.

Every existing radar rebinds its traffic through `RebindTraffic` during the transition, including the inactive flat fallback while the console is active. This lifecycle operation does not advance the engine, refresh a readout, rasterize or upload. Hidden radars skip ordinary updates, so waiting for the next visible frame would retain an old traffic pack across a switch. `HarborReplayTests` verifies that the hidden radar releases that pack and that retired run environments, day packs and traffic monitors become collectible.

`V05CompositionTests` exercises the real scene's dialogs, text entry, live/restarted preferences, shared pictures, camera demand, alarm keys and pointer softkeys, synchronized rebindings, transient pop-outs, lifecycle, recording parity and the all-on allocation contract (strict-zero machinery, only documented clock/first-seen-value strings, zero on trajectory replay). `V05CaptureTests` is explicit: day/night 1920×1080 eye, classic and unobscured focus views, console pop-outs, paused options and key hints under `artifacts/v05-integration/captures`. The separately explicit allocation diagnostic only attributes failures; it never substitutes for the strict guard.

## Session input and chart alarm choices

`HarborTextEntryGate` follows the active wheelhouse view once and publishes its Save As text focus synchronously. The bootstrap holds the helm, presentation holds alarm keys and the camera rig, and displays disable their action map and discard all pending commands on entry. Text editing and menu navigation remain active. Rebound buttons follow the same gate; camera buttons require a fresh press after release. Continuous free-fly movement held physically through release resumes as a value input.

The active chartplotter supplies the session's CPA limit, TCPA limit and mute choice to `HarborDisplays`. Replacement console views and newly activated flat views receive those values before they are used; neither settings files nor recordings store them. Skin pointer hits consider only the visible page, from the last drawn softkey to the first. A page change cancels a held key if it is hidden.

The display capture fixture explicitly preserves its settings and layout stores when replacing its render target. `WheelhouseUI.Configure` is a setup API that supplies fresh temporary stores unless stores were configured explicitly; normal player resolution scaling uses the existing `PanelSettings` and does not call it.
