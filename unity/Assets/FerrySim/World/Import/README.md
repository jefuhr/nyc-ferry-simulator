# Lower East River Import

The importer builds a reusable `Generated/LowerEastRiver/lower-east-river.prefab`, tiled depth meshes, chart structure colliders, navigation aid lights and oriented landing contact strips. It does not modify the world scene or connect the physics bridge.

## Rebuild

From the repository root:

```sh
mkdir -p artifacts/unity
uv run --project data-pipeline python data-pipeline/ferrydata build --slice lower-east-river
uv run --project data-pipeline python data-pipeline/ferrydata export-unity --slice lower-east-river
lockf -k "$HOME/FerrySim-cache/unity.lock" /Applications/Unity/Hub/Editor/6000.3.27f1/Unity.app/Contents/MacOS/Unity -batchmode -nographics -quit -projectPath "$PWD/unity" -executeMethod FerrySim.World.Import.SliceImporter.Import -logFile "$PWD/artifacts/unity/import.log"
```

In the Editor, use **FerrySim > Import > Lower East River**. Keep the `.meta` files: re-import updates assets in place and preserves GUIDs. The importer owns only `Generated/LowerEastRiver/` and removes stale outputs there. Keep hand-authored assets elsewhere.

Run tests with `-batchmode -nographics -runTests -testPlatform EditMode -testFilter FerrySim.World.Import.Tests -testResults <absolute XML path> -logFile <absolute log path>` under the same lock, without `-quit`. Run `FerrySim.World.Import.ImportScreenshots.Capture` in batchmode **without** `-nographics` to generate `artifacts/unity/import-*.png` using URP.

## Coordinates and resolution

Every lon/lat goes through `LocalTangentPlane.World.ToLocal`, then Unity `(east, NAVD88 + geoid, north)`. The geoid comes from `geoid_offset.json`'s slice centre, matching the slice-wide datum convention; the published corner variation remains in the source file. The raster exporter converts CUDEM NAD83 coordinates to WGS84 using installed GDAL/PROJ with nearest-neighbour sampling, one thread and no network fetches. The raw grid is little-endian float32, row-major, with sample centres at origin plus `(column + .5, row + .5)` times cell size.

Terrain samples every fourth raster cell, approximately 12 m, and retains the last row/column. Tiles contain at most 65 by 65 vertices. Nodata is omitted, never replaced by invented bathymetry. Vertex colours show shallow cyan through deep blue and positive NAVD88 terrain in green/brown.

Chart line/polygon structures become double-sided MeshCollider strips on `Structure` (layer 8). Their vertical extent, NAVD88 -60 to +1 m, is a deliberately approximate greybox extrusion, not a surveyed structure height. Point-only chart objects have no supplied extent and are reported as omitted. A landing's floating barges and berths are omitted too: every structure whose `lnam` contacts.json gives for a barge-kind segment (`berth-face`, `barge-side`, `barge-end`), nine PONTON outlines, listed in the manifest's warnings. The greybox draws them on the tide, where a fixed extrusion to +1 m would stand above the deck whenever the water is below -0.2 m. The other floating chart structures (PONTON, HULKES) are still extruded fixed. The import manifest records all input SHA256 hashes, counts and limitations.

## Lights

`LightCharacteristic` supports `F`, `Fl`, `LFl`, `Q`, `Iso`, `Oc` and flash groups, including `Fl(2+1)`. Only nonempty, valid sequences marked `UsesChartSequence` override nominal timing; empty serialized arrays use the fallback. Published `SIGSEQ` durations must sum to the chart period. When the chart supplies rhythm and period without a sequence, pulse widths are visibly labelled nominal in the manifest: Fl 0.3 s, Q 0.3 s at 1 Hz, LFl 2 s, Iso 50 percent duty, Oc 75 percent duty. Short-period flash groups compress their nominal pulse widths and spacing together, preserving every flash, a longer gap between composite groups, and a final eclipse. Grouped occulting lights preserve every eclipse, with longer light between composite groups. Long flashes retain 2 s pulses and compress gaps; infeasible periods and grouped fixed lights require chart SIGSEQ or produce an explicit import warning and remain grey markers. Unsupported characteristics or missing periods also remain grey markers. The supplied slice contains three such period-less fog lights and one nominal-width light; consult the generated manifest for current counts.

Published `height_m` values are above MHW. The importer verifies the cached `datums_8518750.json` bytes against `data/manifests/coops.json`, then adds `MHW - NAVD88` from NOAA CO-OPS The Battery (8518750), followed by the slice geoid offset. The cache follows the pipeline's `FERRYSIM_CACHE` override, defaulting to `$HOME/FerrySim-cache`. Missing, mismatched, non-metric, or incomplete datum data stop the import. `import-manifest.json` records the source URL, checksum, epoch and both station-datum elevations. This uses one station relationship across the slice rather than a surveyed local datum surface. Lights with unpublished heights retain an explicit greybox estimate of NAVD88 +3 m.

`BuoyFlasher.SetSimulationTime(seconds)` accepts scenario time from a bridge; until called, standalone previews use elapsed Unity play time. Every source light has its own flasher. Greybox lens and light colour follow the chart, while beacon/buoy hull models remain generic.

## Contact geometry

**Version 2 (wave 2a).** The importer reads `data/processed/lower-east-river/unity/contacts.json`, which `ferrydata export-unity` writes from `landing_structures.geojson` (schema in `data-pipeline/README.md`, contacts.json version 2): each landing's whole structure, the barge's every side and end, every berth of the stop, nearby pontoons, and the piers, bulkheads and shoreline within 150 m. For every record it recomputes `start_ne_m`, `end_ne_m` and `water_normal_ne` through the core's `LocalTangentPlane` from `start_lonlat` and `end_lonlat` (`SliceImporter.ContactRecord`), so positions match the world to the bit; it refuses an unknown `kind`, an id outside 1 to 2^31-1, a segment under 1 mm, pipeline coordinates more than 1 mm from the core's, a duplicate id, a stop without a primary face, and any landing whose exposed run (`landing-<stop>`) does not keep the physical-edge ids this importer derives from `landing_faces.geojson` (`LandingSegments`). The file is still a bare array with every version 1 field first, so a version 1 reader loads it; the existing 40 segments keep their ids, end points and flags, and only South and North Williamsburg's crew-reported primary faces change `verification` to `crew-reported`. `import-manifest.json` records `contacts_version`, `contact_segments`, the count per kind and the hash of the exported file. A grey contact strip goes under `Landings/<stop>` for every fixed segment (`pier`, `bulkhead`, `shoreline`), named `<stop>-Contact-<i>` by the segment's place among the stop's records, the landing's exposed run first. Barge kinds get none: the barges float and the greybox draws their sides on the tide, where a strip fixed at NAVD88 +0.18 m would stand above the deck at low water.

The rest of this section describes the version 1 fields, which keep their meaning. `contacts.json` contains stable positive IDs, stop identity, double-precision `start_ne_m`, `end_ne_m`, `water_normal_ne` and source/confidence/verification fields. `properties.contact_geometry`, when present, is an already oriented connected polyline, read in source order with a separate water-left normal for every segment. Its short ends must not be reversed toward the primary face normal. Optional `polyline_id` and zero-based `index` preserve membership and order; adjacent end/start pairs are identical. The importer falls back to the legacy `properties.face_geometry` line and orientation rule for older slice data. IDs are a deterministic hash of stop id, source-outline identity (`enc:<ENC id>` or `derived-barge:<stop>:<fixed-shore id>`), and physical edge ordinal. The outline is canonicalized to clockwise winding from its lexicographically smallest WGS84 vertex. Neither primary/end role, eligibility, contact order nor primary selection enters the ID. The coordinator approved a one-time migration from the pre-merge role-based IDs; its complete mapping is in the fix handoff. Legacy face-only inputs without a polygon use order-independent endpoint identity. Geometry confidence uses only `high`, `medium`, or `low`; derived ends have `low` confidence and optional `geometry_estimated: true`. The feature's polygon is the structure outline, not the contact line. All GTFS stops require a face; missing ones fail the import.

Optional `primary_face: true` marks every subsegment of the stop’s selected primary landing face, exactly as selected by the pipeline. It is absent on all other outline sides. Each stop has at least one flagged segment, and its flagged indices form one contiguous run. Primary membership is independent of eligibility, confidence and crew provenance; consumers can use it to aim scenarios at the selected face without guessing from segment order.

The bridge can construct `ContactSegment`s and then `SegmentListGeometry` from this file. ContactSurface calibration is intentionally absent: the bridge must supply reviewed material parameters. The pipeline's `needs-crew-verification` and derived-face confidence remain explicit; these assets are not surveyed berth acceptance.

World.Import tests that read processed slice data skip only when the entire slice directory is absent, with the full build and export commands in the reason. An existing but incomplete or malformed directory still fails. Synthetic geometry and runtime tests continue running without processed data.

Optional `water_side_crew_reported: true` is emitted only on primary-face subsegments when a tracked crew note supplies that face's water-side orientation; ENC-derived end-side normals do not inherit the crew flag. `water_side_verified_by_pipeline` reads the matching `contact_segment_evidence` entry and independently reflects that side’s chart check; only the primary face’s own subdivisions share the primary proof. Other sides require independent evidence. Missing evidence for an end defaults to false, including legacy connected inputs; crew support never turns a failed chart check into a pass. Both may be true (North Williamsburg has crew orientation plus a WATLEV-aware corridor check). The crew-note file checksum is embedded in the landing input and therefore covered by the import manifest hash. Pier 11's general ramp-berth statement is optional `crew_evidence` provenance (`note_id` and `kind: berth-use-policy`) and leaves ordinal geometry confidence unchanged but does not assert a crew water-side direction, so it has no crew water-side boolean.

Optional `water_side_evidence` records the direct or corridor proof per contact segment. Optional `crew_evidence` records face-orientation provenance only on that primary face, or general berth-use-policy provenance on the selected pontoon. The runtime chart-OR-crew inclusion filter can shorten an exported polyline; original indices/IDs remain and missing sides must never be bridged. The validation report lists retained/dropped indices and each connected open run.

South Williamsburg (stop 8) now flags only its NW long side as primary, with the dated `south-williamsburg-face-orientation-2026-10-24` crew evidence. Its failed chart check remains false; runtime eligibility comes from the separate crew flag. The SW end keeps its independent chart proof without crew support. Existing physical IDs and the contact outline are unchanged by the primary-role selection.
